# Cravio — step-by-step setup and copy/paste guide

The files have already been implemented in this folder. For another computer, use `deliverables/Cravio-complete-source.zip`; it includes the photographs. `deliverables/COPY_PASTE_FILES.md` contains complete text files, each labeled with its destination. Binary photos cannot be pasted as source code.

## 1. Keep a backup

Copy your current project folder before replacing files. Back up an existing PostgreSQL database with your usual `pg_dump` workflow. Keep your existing `backend/.env` private. The supplied ZIP deliberately excludes secrets, node_modules, build output and test databases.

Do **not** execute `backend/db/schema.sql` on an existing database: its original reset statements delete tables. The migration command below detects an empty database and only bootstraps it then; otherwise it applies additive migrations.

## 2. Install prerequisites and dependencies

Use Node.js 22.12 or newer ([Node 24 LTS](https://github.com/nodejs/node/releases) is a suitable choice) and PostgreSQL 16 or newer. Validation in this checkout used Node 26 and PostgreSQL 16. Install with your normal package manager, then open a terminal in `Cravio`:

```bash
npm ci --prefix backend
npm ci --prefix frontend
npm run setup
```

`setup` creates missing `.env` files and generates a random JWT secret. It never overwrites existing configuration. If you already have `.env`, copy the additional settings from the supplied examples into it.

## 3. Configure the database

Create a database with PostgreSQL tools, for example:

```bash
createdb cravio
```

Edit **backend/.env**, replacing the example credentials with your local PostgreSQL credentials:

```dotenv
PORT=8000
DATABASE_URL=postgresql://YOUR_DB_USER:YOUR_DB_PASSWORD@localhost:5432/cravio
JWT_SECRET=YOUR_EXISTING_OR_GENERATED_RANDOM_SECRET_AT_LEAST_32_CHARACTERS
CORS_ORIGIN=http://localhost:5173,http://127.0.0.1:5173
NODE_ENV=development
ALLOW_MANUAL_PAYMENTS=false
ENABLE_GOOGLE_PLACES=false
GOOGLE_PLACES_API_KEY=
ADMIN_NAME=Platform Admin
ADMIN_EMAIL=YOUR_ADMIN_EMAIL
ADMIN_PASSWORD=YOUR_UNIQUE_ADMIN_PASSWORD_AT_LEAST_12_CHARACTERS
ADMIN_PHONE=YOUR_PHONE_NUMBER
ALLOW_DEMO_SEED=false
DEMO_PASSWORD=
```

Use URL-encoded characters in the database URL if your database password contains `@`, `:`, `/` or other URL characters. Do not copy the placeholder JWT or password values literally. Keep the secret generated by `npm run setup` when it created the file.

Check **frontend/.env**:

```dotenv
VITE_API_URL=http://localhost:8000
```

Run at the project root:

```bash
npm run db:migrate
npm run db:doctor
npm run seed:admin
```

The migrator records file checksums and refreshes the checkout function, rating trigger and delivery procedure. Do not edit an already applied numbered migration: add a new migration instead.

## 4. Add real restaurant names, logos and food photos

```bash
npm --prefix backend run catalog:real:check
npm run seed:real
```

`seed:real` imports **nine restaurants — Kacchi Bhai, KFC, BFC, Chillox, Sultan's Dine, Khana's, Domino's Pizza, Takeout and Fry Bucket — carrying 95 branches and 237 menu items** between them. Every restaurant has an outlet in all eight divisions (three or four in Dhaka), and the older sample restaurants are topped up to match. The source snapshots publish one record per outlet; `backend/scripts/buildBrandCatalog.js` folds each brand's outlets into a single restaurant with many branches, which is the shape the rest of the app expects. It uses the local files under `backend/data/images/`. Menus and branch details are snapshots of their published sources; the detail page links to those sources. No fake customer ratings are seeded.

The import also creates one restaurant owner login per brand, using `BRAND_OWNER_PASSWORD` (or `DEMO_PASSWORD`) from `backend/.env`:

| Brand | Owner email |
|---|---|
| Kacchi Bhai | owner.kacchibhai@cravio.test |
| KFC | owner.kfc@cravio.test |
| BFC | owner.bfc@cravio.test |
| Chillox | owner.chillox@cravio.test |

The last five are marked `is_demo`, so their cards read "Sample restaurant": they are real businesses, but their menus and prices here were written by us and their food photos are freely-licensed stock pictures of the dish. They are fully orderable all the same. Their dish photography comes from Wikimedia Commons with author and licence recorded in `backend/data/commons-photo-sources.json`; Domino's logo is the real one (freely licensed), while the four Bangladeshi chains get a plain generated wordmark because their real logos are not licensed for redistribution.

If the photos are missing, run `node backend/scripts/fetchCommonsPhotos.js` from the project root — it needs one-off internet access and resumes where it left off.

The four sourced brands are imported with ordering **enabled**, so the full checkout → delivery → review lifecycle can be demonstrated against a real menu. That is a coursework decision, not a merchant relationship: no order reaches a real restaurant and no money moves. Source links and photo credits stay on every page. Real merchant onboarding still needs the verification work in [REVIEW.md](REVIEW.md).

The same command finishes by attaching an illustrative stock photo to any restaurant or dish whose source published none — the original sample restaurants, and 48 BFC/Chillox dishes. Everything it writes is flagged `image_is_illustrative`, which makes the menu print "Illustrative photo" beneath the image, and it never overwrites a photo that is already there. To run only that part later: `npm --prefix backend run photos:backfill`.

Run any of these again safely: matching catalog slugs, branches and menu item names are not duplicated, existing owner data/prices are preserved, and existing passwords are never reset. This is an insert-only importer, not automatic price synchronization. Reviewed corrections to existing entries require an explicit data update.

The four catalog JSON files can also be validated/imported individually from the backend directory:

```bash
cd backend
node scripts/importCatalog.js data/official-chillox.json --check
node scripts/importCatalog.js data/official-chillox.json --apply
```

The former generated, unverified fallback was removed. API errors now stay visible instead of displaying guessed prices and reviews. A backup of those six pre-change source files was retained at `/tmp/cravio-unverified-catalog-backup` on this development machine only.

## 5. Add an orderable local demonstration

To exercise checkout and all delivery roles, set the following in `backend/.env`:

```dotenv
ALLOW_DEMO_SEED=true
DEMO_PASSWORD=CHOOSE_A_LOCAL_TEST_PASSWORD_OF_AT_LEAST_8_CHARACTERS
```

Then run at the project root:

```bash
npm run seed:demo
```

It adds eight **fictional** restaurants, one per division, with 32 photographed sample menu items. Photos are honestly labeled illustrative. Useful demo accounts are:

| Role | Email | Password |
|---|---|---|
| Customer | ayesha@example.com | Your DEMO_PASSWORD |
| Restaurant owner | nabila@example.com | Your DEMO_PASSWORD |
| Rider | jahangir@example.com | Your DEMO_PASSWORD |
| Administrator | Your ADMIN_EMAIL | Your ADMIN_PASSWORD |

Other sample owners also exist for their restaurants. Existing accounts keep their existing passwords: reseeding does not reset credentials. New signup allows customer, owner or rider; administrators are created by the explicit admin seed.

Turn `ALLOW_DEMO_SEED` off again after seeding. The import is blocked in production. Test orders do not place orders with external restaurants or move money.

## 6. Start the app

Terminal 1, at the project root:

```bash
npm run dev:api
```

Terminal 2, also at the project root:

```bash
npm run dev:web
```

Open **http://localhost:5173**. API health is at **http://localhost:8000/api/health**. Keep the frontend URL in `CORS_ORIGIN`; if either port changes, update the corresponding `.env` and restart.

Suggested walkthrough:

1. Browse the real directory, change divisions, search BFC/Chillox/KFC/Kacchi, open logos, galleries and menu previews.
2. Log in as the demo customer. Save an address, favorite a sample restaurant, choose food/modifiers and check out with cash on delivery.
3. Log in as the owner of that sample restaurant. Confirm the order and move it to preparing.
4. Log in as a rider, go available, accept the preparing order, mark pickup, then delivered. Cash on delivery settles when delivery completes.
5. Return to the customer to view the order history/timeline and leave a delivered-order review.
6. Use the admin account to view orders, suspend/reactivate users, manage promotions and respond to support tickets.

## 7. Expand the real catalog and add live city search

Read **[DATA_SOURCES.md](DATA_SOURCES.md)**. Google Places requires your own enabled API project, billing and a server-only API key. Add it to `backend/.env`, not to chat and never to `frontend/.env` or a `VITE_` variable. The `/directory` page performs searches only when requested; no key is bundled.

For owner-supplied datasets, copy `backend/data/catalog.template.json`, fill verified fields, create the actual owner's account, then validate before applying. A source URL or `owner_verified` flag is not independent proof of business identity: the operator must verify the merchant and rights before enabling ordering.

The current owner studio can create restaurants, branches, categories, food photos, modifiers and availability. Existing public directory entries have no owner. Linking one to a verified merchant and enabling its ordering requires an operator-controlled onboarding process; do not assign them to demo accounts.

## 8. Validate changes

```bash
npm run lint
npm run build
node --test backend/tests/catalog.test.js
```

For the backend integration suite, create a **different, disposable** database and set `TEST_DATABASE_URL` in `backend/.env`:

```bash
createdb cravio_test
```

```dotenv
TEST_DATABASE_URL=postgresql://YOUR_DB_USER:YOUR_DB_PASSWORD@localhost:5432/cravio_test
```

```bash
npm run test:backend
```

The test harness requires a database name ending `_test` or `_review`, rejects the application database, installs schema/migrations, seeds test accounts, starts a temporary API, runs the suites and stops that API. It creates test orders and users; never point it at business data.

## 9. Generate the full copy/paste handoff

```bash
npm run package:handoff
```

Outputs:

- `deliverables/Cravio-complete-source.zip`: complete project and 312 local image assets (304 official and 8 illustrative), excluding configuration secrets.
- `deliverables/COPY_PASTE_FILES.md`: full text contents of source/configuration examples, each under its exact path.
- `deliverables/MANIFEST.json`: file sizes and SHA-256 checksums.

For another checkout, extract the ZIP and follow steps 2–6. `.env.example` files are templates; existing secrets are not in the package.

## Common issues

| Symptom | Fix |
|---|---|
| Database connection refused | Start PostgreSQL and check DATABASE_URL and its port. |
| API reachable but missing columns/functions | Run the migrator against the same database the API uses. |
| Migration checksum mismatch | Restore the applied migration file; create a new numbered migration for new work. |
| Blank/failed food photos | Check API connectivity and `/media/...`; copy the images directory from the ZIP. |
| Add button says "Preview only" | That restaurant has `ordering_enabled = false`. The four sourced brands are imported orderable; re-run `npm run seed:real`. |
| Restaurant opens as a different restaurant | A stale frontend build. Restart Vite; the local substitute catalogue that caused this was removed. |
| Dishes show 🍽️ instead of a photo | Run `npm run photos:backfill`, and check the API serves `/media/<file>` from `backend/data/images`. |
| Login works but browser API calls fail | Check CORS_ORIGIN matches the frontend's exact scheme, host and port. |
| New settings have no effect | Restart API; restart Vite after changing frontend environment variables. |
| Port 5173 already used | Close the other dev server or adjust CORS_ORIGIN for Vite's actual port. |
| Google live search unavailable | Enable Places API (New), configure the server key, billing and key restrictions; restart API. |
| Demo password changed but login unchanged | Seeds preserve old passwords. Use the original test credentials or a separate new test database. |
